Architecture Report

Veridian Blue Carbon Credit Registry

System Overview and Technical Analysis of Blockchain Integration Issues

1. Executive Summary

The Veridian Blue Carbon Credit Registry is a web-based ecosystem designed to manage, verify, and trade blue carbon credits. The system enables Non-Governmental Organizations (NGOs) to submit ecological restoration projects, allows administrators to audit and mint carbon credits, and lets companies purchase these credits to offset their emissions.

While the frontend and database layers operate under standard web architecture, the local blockchain layer (implemented using Hardhat and ethers.js) introduces operational instability and connection failures. This report outlines the current structure of the registry and diagnoses the primary root causes of these blockchain-related failures.

2. System Architecture Overview

Frontend Layer

Built with Vite, React, and Tailwind CSS. It communicates with the backend via API endpoints to register users, submit projects, and purchase tokens.

Database Layer (Supabase)

Maintains persistent state for user profiles (roles, approval status), submitted projects, token transaction history, and wallet addresses.

Backend API Server

An Express.js Node server that coordinates authorization, handles project validation, and executes database queries and blockchain transactions.

Blockchain Layer (Hardhat)

An ERC-20 smart contract (CarbonToken) deployed to a local developer network simulating token minting and expiry-based credit transfers.

3. Smart Contract Design

The blockchain logic is contained in the CarbonToken.sol contract, which inherits standard ERC-20 structures from OpenZeppelin. It supports three major operations:

  • Minting (mint): Allowed only for the admin. It creates new tokens (Veridian Carbon Credits, "VCC") and assigns them to the NGO that registered the project.
  • Transferring with Expiry (transferWithExpiry): Transfers tokens to a company while logging an expiration timestamp.
  • Burning (burn): Destroys tokens to permanently retire carbon credits.

4. Analysis of Blockchain Failure Points

The issues causing login, registration, and credit transfer actions to fail are primarily due to how the local blockchain node is integrated with the web application:

Issue A: Hardhat Node Lifetime & Local Network Offline

The backend expects the local Hardhat blockchain network to be running at http://127.0.0.1:8545. Because this node is run locally via command line (npx hardhat node), if it is not explicitly started, or if it crashes, the backend cannot connect. This results in connection failures (like ENOTFOUND or fetch failed) which stall all operations.

Issue B: Database & Blockchain State Desynchronization

Whenever the local Hardhat node is restarted, the entire local blockchain state is wiped clean, and account balances return to zero. However, your persistent database (Supabase) retains all historical records of minted tokens and approvals. This creates a state mismatch: the database reports that an NGO possesses tokens, but querying the smart contract reveals a balance of zero.

Issue C: Nonce & Contract Address Mismatches

Redeploying the smart contract generates a new contract address. If the developer forgets to manually update the CONTRACT_ADDRESS inside the backend’s .env file, the backend continues to send requests to the old address, causing transactions to revert or fail silently.

5. Recommended Strategic Solutions

To move the project from a local developer simulation to a stable environment, we recommend implementing the following changes:

  1. Migrate to an Ethereum Testnet: Deploy the CarbonToken contract to a permanent public testnet (like Sepolia or Holesky) using services like Infura or Alchemy. This ensures the blockchain is always online and doesn't get wiped.
  2. Implement a Web3 Wallet Provider (Metamask) on Frontend: Instead of executing blockchain transactions on the backend using a single private key, allow users to sign transactions directly from their browser using a browser extension wallet (like MetaMask or WalletConnect).
  3. Implement Blockchain Event Listeners: Rather than updating Supabase immediately inside Express controllers, set up event listeners that watch the blockchain for transaction confirmations and update the database asynchronously once the transaction is finalized on the ledger.
